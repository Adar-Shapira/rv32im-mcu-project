Clause 8 UART menu firmware -- tools/gen_uart_menu.py
154 instructions. ONE program, TWO data images: the ITCMs are
byte-identical and only the V_HALFSEC word differs.

  menu/     BTCMPR0 = 9,999,999 -> 0.5 s at SMCLK = 20 MHz
  menusim/  BTCMPR0 = 1,999 -> a tick every 2000 cycles

  Item 1 counts on PORT_LEDR, not LEDG: clause 4's interface is the ten
  RED LEDs and clause 5's table has exactly one LED register. The board
  does have LEDG[8:0] (Terasic CSV) but no register reaches it. R2.

Handlers (byte addresses, written into the vector table by the program):
  ISR_RX   = 0x022c  -> DTCM word 2 (TYPE 08h)
  ISR_BT   = 0x0238  -> DTCM word 4 (TYPE 10h)
  ISR_KEY1 = 0x0244  -> DTCM word 5 (TYPE 14h)

DTCM layout, byte addresses:
  0x0020 V_MODE      0x0024 V_VALUE
  0x0028 V_TICK      0x002c V_CMD
  0x0030 V_KEYMSG    0x0034 V_SENDPTR
  0x0038 V_HALFSEC   0x003c V_KEYARM
  0x0040 the menu, 203 characters, one per word
  0x0400 the message, 17 characters

THE SCENARIO, which tb_uart_menu.vhd reproduces with real serial timing:
  1. collect the startup menu           -> send '2'
  2. four LED values from 0xFF          -> send '1'
  3. four LED values from 0x00          -> send '3'
  4. LEDs cleared and the count stops   -> send '4'
  5. press and RELEASE KEY1             -> collect the message
  6. send '5'                           -> collect the menu again

Expected transmitted stream: 423 characters = MENU(203) + MESSAGE(17) + MENU(203).
Expected LED sequences: ['0xff', '0xfe', '0xfd', '0xfc'] then ['0x0', '0x1', '0x2', '0x3'], then 0x00 and no further writes.
The interpreter completes the scenario in 47092 emulated cycles
(with a shortened frame time; the RTL run is longer because a real
8N1 frame at 115200 is 10*16*11 = 1760 cycles).
